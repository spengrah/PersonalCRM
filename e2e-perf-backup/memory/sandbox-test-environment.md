UPDATE 2026-07-17 (CPU CAP — matters for ALL perf work here): this container is cgroup-v2 CPU-capped at **2.0 CPUs** (`/sys/fs/cgroup/cpu.max` = `200000 100000`) even though `nproc` reports **10** — `nproc` LIES about the real budget. It is chronically CFS-throttled. `cpu.max` is read-only inside (host/VPS-controlled; can't raise it from the container). Consequence, measured across sandbox/Mac/CI on `3220ad8`: E2E is CPU-bound and oversubscribing workers past the quota is SLOWER (full suite: 4 workers on the 2-CPU cap = 562s vs 440s at 2 workers; the Mac at 12 CPUs runs the same suite in 45s). So the sandbox is ~12× slower than a 12-CPU box purely due to the cap — not the tests. gh #425 shipped a cgroup-quota-aware worker heuristic in `frontend/playwright.config.ts` (#686, develop `7c08d24`) that reads `cpu.max` (via `/proc/self/cgroup`) and sizes the Playwright pool to the quota (sandbox→2, 4-CPU→3, 8-CPU→4, Mac→4); it auto-scales if the host raises the container's CPU allocation. The real E2E speed win here is raising that allocation (host action). Measure CPU via cgroup `cpu.stat usage_usec`/`throttled_usec`, NOT host `/proc/stat` (which reports all 10 host cores + other tenants). See [[measure-dont-assume]].

This sandbox has NO docker; Postgres 16 runs natively on localhost:5432 (`make postgres-native` path). `personal_crm_test` exists; connect with `PGPASSWORD=crm_password psql -h localhost -U crm_user`. `crm_user` was granted SUPERUSER (2026-07-02) so the integration harness can create the `vector` extension in its template DB. Integration tests run directly: `DATABASE_URL="postgres://crm_user:crm_password@localhost:5432/personal_crm_test?sslmode=disable" LONG_TESTS=1 go test -tags integration_testdb ./tests/` from backend/, or `make test-integration`. E2E (Playwright) is NOT runnable here (needs the docker stack) — rely on CI's full suite and say so in PR verification notes. Pre-push hooks: this checkout was originally provisioned WITHOUT `make setup`, so `core.hooksPath` was unset and no hooks fired (pushes bypassed the gate). FIXED 2026-07-03: ran `scripts/install-git-hooks.sh` (sets `git config core.hooksPath scripts/hooks`) — now active in this checkout and all its linked worktrees (shared config; `extensions.worktreeConfig` unset). Also set a global `init.templateDir=~/.git-templates` with a guarded bootstrap `hooks/post-checkout` that auto-runs `scripts/install-git-hooks.sh` on any FUTURE clone that ships it (tested). The pre-push `check_review_log()` gate blocks a push unless `.ai/log/review/<HEAD-sha>.md` contains `RESULT=PASS` (i.e. `/review-head` must pass on the exact HEAD being pushed). Merging via `gh` is server-side and does NOT run the local hook, but land only review-head-passed HEADs anyway. `codex review --base develop` works for pre-PR review (takes a custom prompt only with --uncommitted/--commit forms, not with --base).
