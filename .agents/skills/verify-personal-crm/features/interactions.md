# Interactions

The Interactions page (`/interactions`) has two tabs under a heading and the Review switch. The Interactions tab lists every interaction across contacts, to correct frequency data. The Threads tab lists one row per thread and opens each on its own page (`/interactions/threads/<thread id>`), where, with Review on, the user labels message flags. Expected behavior lives in `spec/interactions.yaml`; this file says how to drive it here.

## Sub-features

- `IXN-074` the heading, the Review switch and the two tabs, the tab part of the address.
- `IXN-075` the Review switch: one setting for the list and every thread page, kept across visits; with it off no judgment shows.
- Interactions tab: `IXN-041` the list, its rows and pagination, `IXN-051` the route behind it; `IXN-042` the type and contact filters; `IXN-037` remove and `IXN-038` merge from a row's menu; `IXN-050` the link in from a contact's history.
- Threads tab: `IXN-076` one row per thread, its filters and paging; `IXN-077` Review on: the Run filter, each row's judged count and status pill, the summary line; `IXN-087` and `IXN-088` the routes behind them.
- Thread page, Review off: `IXN-078` its address, the navigation bar (Back to list, the Review switch, the pager, arrow keys) and the header kept at the top; `IXN-079` the messages and the "Earlier messages" toggle.
- Thread page, Review on: `IXN-080` the run's nights as one timeline (dividers, judgment boxes, the later-messages toggle, the header's status, run and Done); `IXN-081` flag chips, "+ Flag" and labels shown on every run's chip; `IXN-082` Commitments re-checked; `IXN-083` Done and Next close a thread and nothing else does; `IXN-084` Confirm Nones; `IXN-085` no click waits on the server; `IXN-086` the reply lists. Routes behind them: `IXN-089` the thread read, `IXN-090` and `IXN-091` the flag and clearing labels, `IXN-092` the close, `IXN-093` Confirm Nones, `IXN-094` the statuses, `IXN-096` the review route given a run.
- Not reachable here: reply items in the `live` and `suggested` states and the `Accept`/`Keep`/`Keep original` corrections of `IXN-086`. The instance names no production decision method, so every seeded reply item is `not_acting`. No method can run here, so every run is seeded.

## How to get to it (user POV)

- Choose the `Interactions` nav link (`/interactions`). Below the `sm` width, open `getByRole('button', { name: 'Main menu' })` first.
- Choose the `Threads` tab (`getByRole('tab', { name: 'Threads' })`, address `/interactions?tab=threads`). The Review switch is `getByRole('switch', { name: 'Review' })`, on the page heading's right and in a thread page's navigation bar.
- On the Threads tab, choose a row's `Open thread` link. The thread page's address is `/interactions/threads/<id>?type=&contact=&run=&page=`; the filters in it are the list's, so the pager walks the list as filtered.
- On a contact's detail page, choose `Review in all interactions` to reach `/interactions?contact=<id>`.
- The list addresses: `/interactions?contact=<id>&type=<type>&page=<n>` (Interactions tab) and `/interactions?tab=threads&type=<type>&contact=<id>&run=<run id>&page=<n>` (Threads tab). The Threads tab's `type` is `message`, `email` or `event`.

## Driving it with Playwright

Preconditions:

- Baseline from `README.md`. The `standard` world holds interactions but no thread worth reviewing and no judgment run. Seed both before loading the page, as the E2E specs do (`frontend/tests/e2e/thread-page/helpers.ts` shows the calls):
  1. **A world.** `bin/api POST /api/v1/test/seed/declared '{"behavior_id":"IXN-080","namespace":"<unique>"}'` seeds three contacts in a thirty-message group chat (`board`), a three-message chat (`side`) and a two-message chat of the third contact (`quiet`). `IXN-076` seeds twenty-one one-contact chats, a group chat, an email thread and a meeting. The response names each handle's `id` (the chat handles' ids are interactions, usable as `thread_interaction_id`).
  2. **Threads and messages.** `bin/api GET '/api/v1/threads?contact_id=<id>&limit=100'` lists thread ids in list order; `GET /api/v1/threads/<thread id>` returns the messages with their `message_key` in thread order.
  3. **A run.** `bin/api POST /api/v1/test/judgment-runs '<json>'` with `kind` (`historical` or `scheduled`; `rerun` never lists), `method_key` (`clef-masked`, `clef-masked-reasoned` or `jev-masked`; another key is never listed), `method_version`, `wording_version`, `from`, `to` and `judgments`. One judgment per night: `thread_interaction_id`, `context_kind` (`conversation`), `cut_off`, `window_start` (the first message the window reads), `new_messages` (message keys new at the cut-off), `flags` (`{message_key, kind, probability}`; a probability from 0.3 shows as a chip, a lower one only feeds "Closest unflagged" above 0.05), `clearings` (`{commitment_message_key, commitment_cut_off, done, probability}`, naming a commitment flagged at that earlier cut-off), and for reply lists `ball_in_court` (`{question_id, contact_id, outcome, confidence}`, outcomes `i_owe_reply`, `they_owe_reply`, `nobody_owes`) with `questions` (`{id, probabilities, original_answer}`) that give each empty list its closest decision. A body's `unjudged` lists `{thread_interaction_id, cut_off, message_key, reason}` for new messages no judgment answered (`call_failed`, `message_over_limit`). The route answers `201` with `run_id`.
- **Review switch.** Click it on either page and read `aria-checked`; `localStorage['crm:review']` holds `on` or `off`. Open another thread page or reload and read it again.
- **Interactions tab.** Wait for `getByRole('list', { name: 'Interactions' })`. Rows are `listitem`s carrying `data-interaction-id`; compare with `s.apiGet('/api/v1/interactions?limit=20')`. Page with `getByTestId('pagination').getByRole('button', { name: 'Next' })`. Type: a button in `getByRole('group', { name: 'Type' })` (`aria-pressed` marks the active one). Contact: open `getByRole('group', { name: 'Contact' })`, fill `getByPlaceholder('Search contacts...')`, choose `getByRole('option', { name })` (not exact). The tab shows no Run filter, judgment or review control, whatever the switch holds.
- **Threads tab.** Rows are `[role="listitem"]` of `getByRole('list', { name: 'Threads' })` carrying `data-thread-id`, with `[data-venue-chip]`, `[data-group-chip]`, `[data-thread-title]`, `[data-participants]`, `[data-count]` and, with Review on, `[data-thread-status]`. With Review on, `getByLabel('Run')` and `[data-run-summary]` appear and the list holds the newest run. Type is a button in `getByRole('group', { name: 'Type' })`, the Interactions tab's control offering All, Messages, Email and Events (`aria-pressed` marks the active one); `[data-venue-chip]` still names each row's app. Compare with `s.apiGet('/api/v1/threads?...')`.
- **Thread page, Review off.** `[data-thread-header]` holds the title (`[data-thread-title]`), chips and participant links; `[data-plain-thread]` holds the messages (`[data-message-key]`, with `[data-message-sender]`, `[data-message-time]`, `[data-message-text]`), the earlier ones behind `getByRole('button', { name: 'Earlier messages' })`. Press `ArrowRight` and `ArrowLeft`, or use `getByRole('button', { name: 'Next thread' })` and `Previous thread`; `Back to list` returns to the Threads tab with the address's filters. Judgment elements (`[data-judgment-box]`, `[data-chip]`, `[data-thread-status]`, `+ Flag`, `Done`) must be absent.
- **Thread page, Review on.** `[data-review-timeline]` holds, per night, `[data-night-divider]` ("{night} · {n} new messages"), the night's `[data-message-key]` messages with `[data-chip="<kind>"]` (`data-chip-state` is `to_review`, `confirmed`, `removed` or `added`) and `+ Flag`, and `[data-judgment-box]` with `[data-judgment-heading]` (its time link scrolls to the message and sets `data-highlighted`), the reply lists, `[data-clearing]` items, `[data-closest-unflagged]` and `[data-judgment-footer]`. Later messages sit behind a `... later messages, after this run's last night` toggle. The header adds `[data-thread-status]`, `[data-run]` and `Done`.
- **Flags.** On a chip click `Confirm <Kind>` or `Remove <Kind>` (`Commitment`, `Big moment`, `Claim`), then `Change <Kind>` on a reviewed one. `+ Flag` opens `getByRole('menu', { name: 'Add a flag' })`; choose a `menuitem`. Find `POST /api/v1/threads/<id>/flag-labels?run_id=<run>` in `api.jsonl`, and read `s.apiGet('/api/v1/threads/<id>?run_id=<run>')` for the chip's recorded state. Open the thread under another method's run to see the same label on its chip.
- **Clearings.** In a box's `Commitments re-checked`, `Confirm clearing` or `Remove clearing` (`[data-clearing-label]` then reads `confirmed` or `removed`); `Show in thread ↑` scrolls to the commitment. Find `POST /api/v1/threads/<id>/clearing-labels` and its `done`.
- **Reply lists.** In a box, `getByRole('group', { name: 'I owe a reply' })` and `Owes me a reply` hold `li[data-item]` with `Confirm <contact name>`, `Remove <contact name>`, `Change the review of <contact name>`, `Add` and a picker group `Add to <list>`; an empty list shows `[data-none]` ("None closest: <name> <n>%"). Find `POST /api/v1/judgment-outcomes/<id>/review?run_id=<run>` in `api.jsonl`.
- **Confirm Nones.** On a night showing nothing, click `Confirm Nones` and find `POST /api/v1/judgments/<id>/confirm-nones`. The button then disappears and the thread reads `Reviewed`.
- **Close.** Click `Done`, press `ArrowRight` or click `Next thread` after labeling, and find `POST /api/v1/threads/<id>/close?run_id=<run>` (`200`) in `api.jsonl`. The footers then read "{n} unflagged new messages labeled none when you moved on". Back to list, `Previous thread`, `ArrowLeft` and following a link must post no `close`.
- **Slow saves.** To drive IXN-085 in the browser, hold a save's response with `page.route`, click the next control, and release: every click is taken, the requests leave in the order made, and a close leaves after the earlier saves are answered.
- **Remove a row, merge rows.** On the Interactions tab, `More actions`, then `getByRole('menuitem', { name: 'Remove' })`; in `getByRole('dialog', { name: 'Remove interaction' })` choose a reason radio (match its start, such as `/^Duplicate/`), then click `Remove`. Find `GET /api/v1/interactions/<id>/participants` and `POST /api/v1/interactions/<id>/removals` in `api.jsonl`. For a merge choose `More actions` → `Merge`, check `Select interaction` on another row, click `Review merge`, wait for `[data-merge-result]` in `getByRole('dialog', { name: 'Merge interactions' })`, then click `Merge` (exact); find `POST /api/v1/interactions/merge/preview` and `POST /api/v1/interactions/merge`.
- **Link in.** Open `/contacts/<id>`, choose `Review in all interactions`, and check the address holds `contact=<id>`.

## Gotchas

- The verify instance sets no `DECISION_PRODUCTION_METHOD`, so reply items read `Not acting` and carry `data-state="not_acting"`.
- A thread page with Review on and no `run` in its address uses the newest run the runs list holds; with no run recorded it shows the plain thread.
- A client-side move to another thread fires no `load` event: wait with `page.waitForURL(re, { waitUntil: 'commit' })`.
- A run's dates and every time on the page show in the browser's time zone, so a `from` at UTC midnight can read as the previous day.
- A rejected `POST /api/v1/test/judgment-runs` (for example an unknown `thread_interaction_id`) can leave an unfinished run behind. Relaunch for a clean run list.
- The switch's track fades for about a third of a second; wait before a screenshot that must show its final color.
- Removals and merges cannot be undone, and recorded runs persist until cleanup. Relaunch for a clean world.
- Only rows of kind `interaction` offer `More actions`; grouped chat rows (`message_burst`) do not.
