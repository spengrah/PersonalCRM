# Change Checklist and Troubleshooting

Read relevant entries when changing shared contracts, database semantics, generators,
or verification tooling, or when diagnosing the listed symptoms. Paths below are
relative to the repository root. Core policy remains in [core.md](../rules/core.md).

## Common Gotchas

Domain entry files retain essential constraints. For detailed symptoms, read the relevant entries in [backend troubleshooting](backend-troubleshooting.md) or [frontend troubleshooting](frontend-troubleshooting.md).

| Mistake | Fix |
| --- | --- |
| `make test` from subdirectory | Run `make` commands from project root |
| `git add -A` includes binaries | Review `git status` before commit, exclude `backend/crm-api` |
| Pre-push timing | The hook reports elapsed time for each static check. Expensive suites run in CI; use explicit local test commands when useful. |
| Merging PRs (UI included) | Follow the [branch model and promotion policy](../rules/core.md#branch-model-develop-default--main-prod). |
| Similar defects elsewhere | Search for related defects to understand impact. Fix those within the task's scope and report unrelated cleanup separately. |
| Using `\n` in `gh` CLI body/comment strings (renders as literal `\n`) | Use a heredoc or multi-line string for `gh pr create/edit/comment` |
| `git diff --quiet` to detect new files | Only sees tracked files; add `git ls-files --others --exclude-standard` for untracked |
| Feature removal only grepping source files | Grep ALL file types (tests, docs, comments) for feature name to catch all references |
| Editing `.claude/CLAUDE.md` directly | It's a symlink to `AGENTS.md` - stage `AGENTS.md` for git commits |
| Trusting that a new gate (CI check, hook, lint rule) works because it passed | A gate that cannot fail is indistinguishable from one that always passes. Prove it FAILS on the bad input: inject the defect, `grep` the source to confirm the injection actually landed, then check the exit code directly (`cmd >/tmp/out 2>&1; echo $?` — a pipe returns the LAST command's status, so `\| tail` masks it). For CI, confirm the STEP ran by name (`gh api repos/{owner}/{repo}/actions/jobs/<id> --jq '.steps[].name'`), since a renamed or mis-gated job that silently stops running looks exactly like a green one. BSD `sed` silently no-ops GNU's `0,/re/` address form, which is one way an injection quietly fails to land. Falsify with an input you expect the gate to MISS, not one you know it catches. |
| Adding new contact list filter | Update the shared WHERE fragment (`backend/internal/db/querygen/contact_list.sql.tmpl`) + run `make contact-queries`, plus repository ListContactsParams/ListContactIDsParams, handler query struct, `frontend/src/lib/contact-list-params.ts` (ContactListContext + parse/build), ContactListParams in types/contact.ts, and the API client |
| Echoing API keys or other secrets in bash commands or tool descriptions | Session transcripts persist across conversations. Read secrets inline from `.env` on the target host without emitting them: `ssh host "API_KEY=\$(grep -oP '^API_KEY=\\K.*' /path/.env) curl ..."`. Never include the literal value in a command visible to the transcript. If a secret already leaked into a transcript, rotate it |
| Test failures during PR rebase work | Verify against `develop` first (`git checkout develop && make test-integration`) — pre-existing failures (e.g. flaky LONG_TESTS-gated scheduler rescuer tests) are not regressions from your rebase. Distinguish before debugging |
| Deleting tests in one commit with "Step N adds replacements" promissory note | Delete tests in the SAME commit as their replacements, or keep old tests until the new ones land and delete in a follow-up commit. A promissory deletion stranded between commits (e.g. long agent work hits auth failure mid-task) leaves the branch in a broken-tests state |
| Inline comments referencing `PR #N`, `Step N`, `Decision N`, `Round-N`, plan names, or "this fix" | These metadata references rot the moment the PR merges. Strip them — keep the underlying rationale (why the code behaves this way) but drop the scaffolding (which PR / step / decision it came from). The PR description is the right home for that context. Applies to `.go`, `.sql`, and any source file comments; documentation (`.md`, `README`, `CHANGELOG`) is allowed to cite PRs |
| Adding a new path-trigger group | `path-filters.yml` is shared by CI and the local static-check selector. Keep flat named groups of quoted globs; update the relevant CI job and `.ai/pre-push.json` check groups. |

## When You Change X, Check Y

Cross-cutting concerns that require checking multiple locations:

| When You Change | Also Check/Update |
| --- | --- |
| Contact soft-delete logic | Identity cleanup, note cascade, contact_method cascade, AND the person node: `ContactService.DeleteContact` propagates `node.deleted_at` (node.id == contact.id) in the same tx so the contact's assertions drop from graph reads (node-level live filter); assertions are retained in the table. The node/contact identity equation is FK-enforced (`contact_id_node_fk`, migration 077) — but the FK does NOT cascade a soft delete (it only guarantees a node row exists), so the manual `node.deleted_at` propagation above stays mandatory |
| Add a column to `contact` | `live_contact`'s projection is frozen at view-creation time; add the column in a migration that recreates the view, or child-table queries reading through it will not see it. `CREATE OR REPLACE VIEW` can only **append** columns, never reorder or remove; anything else needs `DROP VIEW` + `CREATE VIEW`, which fails if another object depends on it |
| Contact merge | `ContactService.MergeContacts` runs the GRAPH merge alongside the existing method/note/interaction transfers: tombstone the loser node (`SetNodeMergedIntoTx` → `merged_into`+`deleted_at`) and re-point its assertions onto the winner (`AssertService.MergeAssertionsTx`). The graph merge runs BEFORE the field-selection knowledge apply so the user's per-field choice is the last writer. The `RepointAssertionSubject/Object` sqlc primitives are called ONLY by `MergeAssertionsTx`, never the normal write path. The dormant `connection` table was dropped in migration 072 (D10), so merge no longer transfers/dedups `connection` rows |
| Query invalidation rules | `frontend/src/lib/query-invalidation.ts` domain events |
| New entity, sync source, or downstream record | Add the matching factory (`synthetic/factory`) + replay/seed coverage (`synthetic/replay` adapter, profile in `synthetic/profiles.go`) to the synthetic toolkit — new features write their own seeding (see `.ai/patterns/synthetic-seed-toolkit.md`) |
| OAuth flow changes | Both callback route AND auth URL endpoint |
| Contact method types | `contact_method` CHECK constraint + `identity.IdentifierType` enum |
| Cadence options | `contact` CHECK constraint + frontend dropdown options |
| `contact.location`/`birthday`/`how_met` write path | These are DERIVED cache columns and the **database rejects a direct write**: the `reject_unauthorized_derived_contact_write` trigger (migration 079) raises unless the transaction has declared `crm.derived_writer='knowledge_cache'` via `repository.SetDerivedWriterTx`. `KnowledgeCacheUpdater` is their sole writer (recompute from the current-accepted `lives_in`/`birthday`/`how_met` assertion). The contact SQL (`CreateContactWithNode`/`UpdateContact`) does NOT write them. Any code that wants to set one MUST emit an assertion via `AssertService` + refresh via `KnowledgeCacheUpdater.RefreshTx` (see `ContactService.knowledge` / `EnrichmentService.assertInferredKnowledge`). Adding a new direct writer of these columns is a bug; route it through the assertion store. The five cadence columns are under the same trigger with owner `cadence` (`CadenceUpdater.applyTx` and the delete-rollback recompute) |
| A migration that backfills any of the eight derived `contact` columns | The trigger is live from 079 onward. Issue `SET LOCAL crm.derived_writer = 'cadence'` (or `'knowledge_cache'`) inside the migration's transaction before the UPDATE, or the migration aborts. The eight: `last_contacted`, `last_interaction_at`, `last_outreach_at`, `last_response_at`, `contact_by`, `location`, `birthday`, `how_met` |
| Scheduled job changes | Scheduler section in `.ai/guides/architecture.md` |
| New sortable contact field | Shared ORDER BY ladder in `backend/internal/db/querygen/contact_list.sql.tmpl` + run `make contact-queries` + handler oneof + `SortField` type + `ContactListParams.sort` |
| New contact list filter param | Shared WHERE fragment (`backend/internal/db/querygen/contact_list.sql.tmpl`) + run `make contact-queries` + repo params + handler query struct + `lib/contact-list-params.ts` + ContactListParams type + API client |
| Wire DTO structs covered by `backend/tygo.yaml` (e.g. `handlers/contact_dto.go`, `api/response.go`) | Run `make api-types` and commit the regenerated `frontend/src/types/generated/*` — the CI generated-artifacts-drift job and the pre-push LINT lane (`make api-types-check`) fail on drift. New JSON payload structs for a covered domain go in the `*_dto.go` file, not the handler file |
| Swagger annotations (`// @Summary`, `// @Success`, …) or any type reachable from one | Run `make api-docs` and commit the regenerated `backend/docs/*` — the same CI job and pre-push LINT entry (`make api-docs-check`) fail on drift AND on generation failure. If swag cannot resolve a field's type it aborts the WHOLE spec, so add a `swaggertype:"..."` tag rather than leaving the type unresolvable |
| Semantic column to table with dedup logic | All FindInWindow queries (add param), unique constraints, repository signatures, service call sites, `make sqlc`, regression test for false-positive case |
| New build/run site for `crm-api` or `crm-admin`, or a new worker/type the binary needs | Build the PACKAGE (`./cmd/crm-api` / `./cmd/crm-admin`), NEVER a file (`cmd/crm-api/main.go`). New workers/types/adapters go in sibling `.go` files in `package main` (e.g. `cmd/crm-api/wire_*.go`) — do NOT inline into `main.go`. Build sites: `Makefile` (build/crm-admin/ci-build-backend/api-build/test-cadence-\*), `.github/workflows/ci.yml`, `.github/workflows/build-images.yml`, `frontend/playwright.config.ts`, `scripts/start-backend.sh`, `scripts/dev-seed.sh`, `infra/install-systemd.sh`. Sole file-mode exception: `swag init -g cmd/crm-api/main.go` (`api-docs`). Confirm the ldflags stamp still lands (`build-images.yml` grep + `TestHealthEndpoint_StampedBuildInfo`). |
| Path-filter groups (`path-filters.yml`) | CI consumers in `.github/workflows/ci.yml`, static-check groups in `.ai/pre-push.json`, and selection tests in `scripts/hooks/test/test-pre-push-filters.sh`. |
| Pre-push static checks (`.ai/pre-push.json`) | Set relevant path groups; an empty list always runs. Verify selection and failure propagation with `scripts/hooks/test/test-pre-push-phases.sh`, which runs in required CI. Do not add runtime-dependent suites to pre-push. |
| Makefile test-parallelism (`test-integration*` `-p`/`-parallel`) | `scripts/test-parallelism.sh` (single-source formula) + the render guard `scripts/ci/test-parallelism-render-guard.sh` + the CI `GITHUB_ACTIONS` 4/4 pin (keep CI byte-identical) |
| Per-worktree test-pg resolver (`scripts/worktree-test-pg.sh`) | Makefile `TEST_DATABASE_URL` default (the `GITHUB_ACTIONS` ifeq split + `$(or $(WORKTREE_TEST_DB_URL),literal)`) + the `worktree-test-pg-ensure` prereq on `test-integration{,-fast,-slow}` + the render guard's section-5 assertions (forced-shared byte-identity + resolver-invocation counts via `CRM_WORKTREE_PG_COUNT_FILE`) + the shim-only unit test `scripts/test/test-worktree-test-pg.sh`. Keep the main-checkout/CI render byte-identical (verified render-vs-render) |
| App logic that changes behavior in a domain with a `spec/<domain>.yaml` file | Follow the [spec maintenance rule](../../spec/README.md#maintenance-rule) and [test citation rules](../../spec/README.md#test--behavior-citations), including stable keys and coverage/waiver requirements. |
| A `type: ux` behavior that carries a `serves:` edge to an intent (or adding such an edge) | Extend the tour that walks that surface (`frontend/tests/tours/*.tour.ts`) so a capture actually EXERCISES the behavior and is tagged with its ID — a `servedBy` entry with no bound capture is a _hollow edge_: the judge grades the intent on evidence that does not exist (see CON-065/CON-051). `make spec-coverage` only gates the deterministic E2E lane; the judge is advisory and out-of-band, so nothing mechanical catches this. Mind the cap: `bindIntentCaptures` slices bound captures by `(tour, seq)` and truncates at `INTENT_CAPTURE_CAP` (8), so a capture added LATE in the tour is silently evicted before the judge sees it — place it early or raise the intent's `captureCap` (`judge/intent-catalog.ts`). Then verify the specific capture is actually BOUND, not just that counts moved: `make qa-report … JUDGE=1` prints only per-intent bound/dropped COUNTS, so run with `QA_JUDGE_TRACE=<file>` and confirm the capture's `(tour, seq)`/`capture_file` appears in that intent's graded evidence. Never assume the edge is enough |
