# `backend/tests/api` (+ `tests/unit/sync_service_test.go`) `t.Parallel()` Audit — Classification Table

Tracking issue: **#429** (the `tests/api` parallelization follow-up deferred by the #430 audit, which covered only the top-level `backend/tests` package). This is the per-file classification of every func-bearing file in `backend/tests/api`, plus the single not-yet-parallelized `backend/tests/unit/sync_service_test.go`, into one of four buckets, with the concrete pre-flip scoping work the implementer executes.

The dominant structural fact for `tests/api`: the package shares ONE Postgres DB at `DATABASE_URL` (`newAPISharedTestDB` via `TestMain`, or file-local `db.NewDatabase` against the same `DATABASE_URL` — both hit the same physical DB; there is no per-test clone). So **namespace-scoping of fixtures/assertions is the dominant lever**, exactly as in #430. Two structural blockers override scoping and force whole clusters serial: (1) the **`mac_host_*` singleton cluster** — `mac_host` is an intentional singleton table (partial-unique `idx_mac_host_singleton`, no `deleted_at`) and its shared setup helpers run DB-wide `DeleteAllMacHosts` / `DeleteAllPairingTokens` teardowns; this is the documented project decision to keep `mac_host_*` serial and cannot be fixed without per-test DB isolation (#428); and (2) **live-River** files that build `river.NewClient(TestOnly:true)` + `Start()` against the shared `river_job` table, where concurrent clients steal each other's jobs — also out of scope until per-test DB isolation (#428).

## Key planning findings

- **The parallelization win comes from the flip-all + scope-then-flip + flip-per-func files (17 of 31).** The 14 stay-serial files (the `mac_host_*` singleton cluster + the 4 live-River ingest files + the 2 schema-migration tests) stay serial and dominate the residual serial time.
- **`mac_host_*` singleton cluster stays serial — KEEP-SERIAL.** Eight files route through `setupMacHostEnv`/`setupKnownIDsByHostEnv`/`setupMeetingNoteIngestEnv`/`setupExtContactIngestEnv` and pair the singleton `mac_host` row + run DB-wide `DeleteAllMacHosts`/`DeleteAllPairingTokens` teardowns. Under `t.Parallel()` two concurrent funcs would (a) collide on `idx_mac_host_singleton` at `PairWithToken` and (b) have one func's teardown delete the other's host/token mid-run (spurious 401s). This is the exact documented project decision. No in-file scoping fixes it; the path is per-test DB isolation or per-test-namespaced host state (#428). Affected files: `mac_host_auth_test.go`, `mac_host_pairing_test.go`, `mac_host_rotate_key_test.go`, `mac_host_janitor_test.go`, `known_identifiers_test.go`, `external_contact_known_ids_test.go`, `external_contact_ingest_test.go`, `external_contact_savepoint_rollback_test.go`, `meeting_note_ingest_test.go`, plus the serial func in `ingest_host_liveness_test.go`.
- **river-heavy funcs stay serial — ref #428.** `ingest_test.go` (17 funcs), `ingest_raw_message_test.go` (10), `ingest_raw_message_e2e_test.go` (1), `phone_call_ingest_integration_test.go` (6), and the **3** river funcs in `tests/unit/sync_service_test.go` (Correction 3) all build a live `river.NewClient(TestOnly:true)` + `Start()` on the shared pool. Even the pure-rejection/validation funcs in these files (no DB write) still construct the live client via the shared setup helper, so they are river-heavy, not scoped-safe. Several also assert DB-wide river-job counts (`countRiverJobs(kind)==N`) that concurrent siblings' same-kind jobs would inflate. Per-test River isolation is the future lever (#428).
- **Go scheduling semantics for mixed packages (Amdahl floor):** within `tests/api`, all non-`t.Parallel()` funcs run to completion sequentially FIRST, then the `t.Parallel()` cohort runs concurrently. The serial mac_host/river funcs gate the parallel cohort rather than overlapping it. The serial fraction is paid in full before any parallel speedup.
- **`tests/unit` is already parallelized except `sync_service_test.go`.** That one file is flip-per-func: 3 non-river DB-backed funcs + 1 pure-unit func flip (their source string literals are already per-func-unique and all DELETE/COUNT queries are `WHERE source=$1`-scoped — no code change needed, just add `t.Parallel()`); the 4 funcs that build a live River client via `mustTestClient` stay serial (#428). NOTE: that file uses raw `pool.Exec` SQL against `river_job`/`external_sync_state` as its existing pattern — do NOT add new raw SQL when flipping; the literals are already unique, so no new queries are needed.
